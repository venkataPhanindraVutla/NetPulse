# Spike findings (2026-10-28)

Machine: macOS 26.6 arm64, Xcode 27.1, Swift 6.4. Primary interface en0. Spike code lived in a scratchpad, not in this repo.

## Known from earlier capture
- `nettop -P -L N -x -J bytes_in,bytes_out` emits blocks, each starting with `,bytes_in,bytes_out,`. Rows look like `Google Chrome H.1135,12527192,992762,` (name truncated to 15 chars, then `.pid`).
- Cumulative mode: a process's bytes can decrease between samples. Use `-d`. In `-d` mode the first block is cumulative and must be discarded.

## Step 1: nettop delta completeness
Command: `nettop -P -d -L 25 -s 5 -x -J bytes_in,bytes_out -t external` (25 blocks, ~2 min) alongside `netstat -ib -I en0` every 5 s, and 50 sequential `curl` downloads of 2 MB from speed.cloudflare.com (the loop finished in about 55 s).

- Block 0 is cumulative (43.3 MB summed inbound) and was discarded; blocks 1-24 are deltas.
- Sum of nettop deltas over the 24 intervals vs interface delta:
  - Inbound: 102,029,100 vs 107,187,067 bytes, ratio **0.952** (meets >= 0.9).
  - Outbound: 1,441,067 vs 4,230,829 bytes, ratio **0.341**. a plausible (untested) explanation is that nettop counts payload while the interface counts ACK/header bytes and other non-"external" traffic. To be checked with an upload test in Task 12. Until then the "Other" bucket absorbs the gap and the README should say outbound totals can sit well under interface totals.
- Per-interval inbound ratios ranged widely (e.g. block 16: 32 KB vs 232 KB, block 17: 204 KB vs 30 KB), so the sampling windows of nettop and netstat are not aligned. Totals over a long window are reliable, individual intervals are not directly comparable.
- Exited processes: 50 distinct curl pids appeared and exited. Summed curl inbound was 100,720,340 bytes against about 100,000,000 requested, so no bytes were lost when processes exited mid-interval. A process reports its last delta in the block covering its exit, then appears with `0,0` for about one further block before dropping out.
- Verdict: `-d` delta mode is usable. Not blocked.

## Step 4: MenuBarExtra `.window` on macOS 26
Initial spike app (`MenuBarExtra` with stacked 9 pt label, plus `--renderer` variant using `ImageRenderer`, which rendered a 50x22 pt template image fine) showed no status item. A follow-up diagnosis used three Location-free apps (LSUIElement, ad-hoc signed, no NSLocation keys), launched with `open`, 3 s wait:
- a0: `MenuBarExtra("NP", systemImage: "arrow.up.arrow.down") { Text("hi") }.menuBarExtraStyle(.window)`
- a1: same with a label closure of a VStack of two 9 pt `Text` lines (the stacked label)
- b: plain AppKit `NSStatusBar.system.statusItem(withLength: .variableLength)`, button title "NP", `.accessory` policy

Results:
- All three processes stayed alive. None had any window owned by its own pid in `CGWindowListCopyWindowInfo(.optionAll)`; on macOS 26 status item windows (layer 25) are owned by Control Centre instead. None of the three appeared in a menu bar screenshot, so **plain NSStatusItem fails identically to MenuBarExtra**. The cause is therefore not Location and not SwiftUI.
- For b, diffing layer-25 windows before and after launch showed exactly one new Control Centre window (x 675, width 38) with onscreen = **no**: the item is registered but not shown. For a0/a1 the diff was noisy (other apps' items shifted), so it is inconclusive but the screenshots show nothing.
- `defaults read com.apple.controlcenter` shows many `NSStatusItem Visible Item-N = 0` keys, consistent with new third-party items defaulting to hidden. The likely cause is the macOS 26 menu bar allow-list ("Allow in the Menu Bar" in System Settings > Menu Bar) which new ad-hoc items start disabled in, possibly with overflow on this crowded bar. Not changed or confirmed (settings are off limits for this spike); this remains a hypothesis.
- SwiftUI stacked label (d): could not be observed because nothing rendered. Unverified whether SwiftUI flattens it; the ImageRenderer fallback remains the safe choice.
- Popover open/close: unverified (osascript has no assistive access).
- Conclusion: neither MenuBarExtra nor NSStatusItem is visible from an ad-hoc LSUIElement app on this Mac as launched here. Owner must check System Settings > Menu Bar for an allow toggle for the spike/NetPulse item and verify stacked label and popover in Task 13.
- Artifacts (kept outside the repo, not published): the initial app log, menu bar screenshots before and after launch for Step 3/4 and for each diagnostic variant (a0, a1, b, b2), and the layer-25 window lists before and after launch.

## Task 12 measurements (2026-10-30)

Probe: `swift build -c release`, `.build/release/netpulse-probe`. Same Mac, Wi-Fi en0 only (identity `wifi:gw:…`; the probe has no Location permission, so no SSID). Reference counters: `netstat -ib -I en0` before and after each run. Raw logs and SQLite files were kept outside the repo.

### Accuracy, download (Step 6)
- The specified `__down?bytes=1000000000` now returns **HTTP 403** with a 1-byte body (so does 1e8; 1e7 works), and the sustained downlink here is about 0.2-0.9 MB/s, so 1 GB in 120 s is not possible. Substitute: a 150 s probe while curl looped `__down?bytes=10000000` (9 requests, 87,987,200 B payload received by curl).
- Interface ↓: probe 135,523,328 B vs netstat en0 Δ 135,540,195 B, ratio **0.9999**. ↑: 4,506,624 vs 4,581,129 (0.984; netstat's window is a few seconds longer at each end).
- curl shown as `curl` (`proc:curl`): ↓ 88,199,324 B vs 87,987,200 B payload, **+0.24%** (TLS/HTTP framing).
- Σapps/total: **down 0.941**, up 0.350.
- A background-only 150 s run (the 403 case) gave probe ↓ 81,215,488 vs netstat 81,229,637 (0.9998); Σapps down 0.960, up 0.790.

### Accuracy, upload
- `dd if=/dev/zero bs=1m count=100 | curl -s -o /dev/null -X POST --data-binary @- https://speed.cloudflare.com/__up` under a 120 s probe, curl capped at 105 s. The sustained uplink is about 360 KB/s, so curl stopped at 37,486,592 B uploaded.
- Interface ↑: probe 43,794,432 vs netstat 43,832,718, ratio **0.999**.
- curl ↑ (nettop) 38,379,638 B vs 37,486,592 B handed to curl, +2.4%.
- Σapps/total: **up 0.903**, down 0.912.
- So the 0.34 outbound ratio from Step 1 (and 0.350 above) is a property of download-heavy traffic: outbound bytes are then mostly ACK frames and TCP/IP headers, which the interface counts but nettop's per-socket byte counts do not (curl sent 4.9 KB of payload against 4.5 MB of interface ↑ during the download test). Under real upload load the ratio is 0.90. "Other / system" absorbs the difference; the README should say outbound "Other" is large while downloading.

### CPU gate (Step 7)
600 s probe runs during light background use (Chrome, WhatsApp etc. running, no manual browsing). Average = (probe + nettop CPU time) / wall time, from `ps -o time=` sampled every 10 s; sampled `%cpu` was also logged.

| Run | nettop interval | probe CPU | nettop CPU | combined avg |
|---|---|---|---|---|
| 1, as built | 5 s | 1.97 s | 829.37 s | **140.2%** |
| 2, nettop stdin fix | 5 s | 4.61 s | 2.31 s | **1.16%** |
| 3, nettop stdin fix | 10 s | 4.71 s | 1.60 s | **1.06%** |
| 4, + reader type cache | 5 s | 1.17 s | 2.50 s | **0.62%** |
| 5, final code | 5 s | 0.89 s | 2.35 s | **0.54%** (sampled mean 0.57%, max 5.6%) |

- Run 1: nettop itself spins at about 140%. Standalone checks (12 s each) gave 141-143% with `-s 5` or `-s 15`, `-n`, `-c`, `-m tcp`, with or without `-d`, all with stdin `/dev/null`. With an open-but-empty stdin pipe it used **0.0%** (0.08 s in 12 s). nettop polls stdin for interactive keys and busy-loops on EOF, so a longer cadence cannot fix it. Fix: `LiveNettopLauncher` gives nettop the pty slave as stdin (never EOF). Crash safety re-checked: `kill -9` of the probe still takes nettop down (SIGHUP).
- Runs 2-3: the probe's own share (about 0.79%) dominated, and a 10 s nettop cadence only trimmed nettop from 0.39% to 0.27%. `sample` showed 64 of 77 tick samples in `SysctlInterfaceReader.systemConfigurationTypes()` (`SCNetworkInterfaceCopyAll` on every 1 s read). Fix: cache the BSD-name → type map while the interface name set is unchanged, with a 60 s maximum age (a just-attached adapter can appear before SystemConfiguration knows its type).
- The 15 s retry was not run: both causes were fixed at the root, and the gate passes at the default 5 s cadence.
- Result: **0.54% combined at the default 5 s nettop cadence. The < 1% budget is met.** nettop is now the larger share (about 0.4%).
- The accuracy runs above used the pre-fix launcher. Counting is unaffected; only nettop's CPU was.

### Other observations
- In run 4, the primary network was unresolved for about 57 of 560 s (36 s keyed `wifi:unknown` because the gateway MAC was briefly missing from ARP, 21 s with no primary), so 8.5 MB went to `wifi:unknown`. The engine now re-resolves an unresolved primary every 5 s for up to 60 s after a change. Run 5 had no flap (558 of 559 lines on the real network), so the retry was not exercised live.
- No `nettop`, probe or curl process was left after any run (`pgrep` checked each time). SIGINT and `--seconds` exits both flush and print the summary.
- After Task 12 fix round 1 (type-cache misses retried every 3 s; unresolved-network traffic parked): a 120 s probe run at interval 5 measured **0.48%** combined (probe 0.17 s, nettop 0.41 s over 121 s). On this Mac every `en*` has a SystemConfiguration type, so the steady state stays on the 60 s cache.

## Final fix wave measurements (2026-10-30)

### nettop interface filter for merged mode (I4)

Question: merged mode used `-t external`, which includes utun, so under a userspace VPN per-app bytes could be counted on the tunnel and on the uplink. Does `-t wifi -t wired` lose coverage without a VPN?

Run: two nettop processes started together, `nettop -P -d -L 25 -s 5 -x -J bytes_in,bytes_out -t external` and the same with `-t wifi -t wired` (25 blocks, ~125 s), while curl downloaded 9 × 10 MB from speed.cloudflare.com (90,000,000 B payload, all complete). Same Mac, Wi-Fi en0 only, no VPN. Reference: `netstat -ib -I en0` before and after (its window was ~160 s, a little longer than nettop's).

| | Σapps ↓ (blocks 2–25) | Σapps ↑ | curl ↓ |
|---|---|---|---|
| `-t external` | 91,270,488 | 638,994 | 90,205,642 |
| `-t wifi -t wired` | 91,270,488 | 638,994 | 90,205,642 |
| netstat en0 Δ | 96,117,666 | 2,983,471 | |

The two outputs were byte-for-byte identical, so coverage is the same (Σapps/total ↓ 0.950 for both; the gap to 1.0 is the usual Other/system plus netstat's longer window). Decision: merged mode now uses `-t wifi -t wired` (`NettopFilter.physical`). A quick check confirmed the filter is honoured (`-t wired` printed nothing on this Wi-Fi-only Mac, `-t loopback` printed only loopback rows).

### Shipping-app CPU (I3)

Changes measured: snapshots are published and assigned only when they change; the menu bar label depends only on its displayed strings and reuses its last rendered image while they are unchanged; split mode needs at least 10 KB/s on both uplinks for 3 ticks; hypervisor and capture interfaces (`vmenet`, `vnic`, `feth`, `pktap`) are virtual; an untyped interface name is retried at most 5 times.

Run: the Debug app was quit, the Release build (`xcodebuild -configuration Release`) launched, label style stacked, popover never opened, Wi-Fi only, light background traffic (no manual browsing). `ps -o %cpu=,time=` for NetPulse and its nettop child every 10 s for 602 s, starting ~15 s after launch.

The < 1% budget is **not met** by the shipping app. A 20 s `sample` of the running app showed the engine (1 s interface read, mostly `sysctl`) at about 25 busy samples and the main thread at about 110: ~43 in `MenuBarImage.stacked` → `ImageRenderer` and most of the rest in the Core Animation commit that pushes the new status item image. With background traffic the three-digit rates change almost every second, so the label is redrawn about once a second even with the image cache. nettop's share (0.58%) is also above the probe runs' ~0.4%, likely from more background sockets during this run. Options at the time (owner's call): draw the label with AppKit text instead of `ImageRenderer`, refresh the label every 2 s, or accept ~1.5% for the stacked label (icon-only already drops to 5 s sampling).

#### After: AppKit label (2026-10-30)

### Owner verification checklist
From Tasks 13, 15 and 16:

1. Make the item visible: System Settings > Menu Bar, allow NetPulse and/or free space right of the notch. Confirm the stacked label updates, in each style (Settings > General).
2. Click the popover: tabs, Apps/History pickers, footer pause/resume, settings and quit (never clicked on the real item).
3. Cap test: set a 0.1 GB monthly cap on the current network, allow notifications, download 100 MB: exactly one 80% and one 100% notification within about a minute; relaunch, no repeat.
4. Launch at login: toggle in Settings > General; confirm it appears and disappears in System Settings > Login Items; check the requires-approval copy if shown.
5. Fresh defaults (`defaults delete io.github.netpulse.NetPulse`), deny Location: the network shows as "Wi-Fi network", the popover shows "New network detected - Name it", renaming works in Settings > Networks. Also grant Location later in System Settings and confirm the name updates.
6. "Name it" and "Set a cap..." open Settings on the right tab. With a daily and a monthly cap set, the Now tab shows the one closer to its limit ("Today" or the month).
7. Invalid cap input (0, -1, abc): inline error, toggle stays off.
8. Real sleep (`pmset sleepnow` or lid): after wake, no negative or doubled totals; the day is not marked (sleep gaps are logged only). Quit NetPulse for over a minute and relaunch: today shows "Not monitored for part of this day".
9. Wi-Fi off/on: no negative or duplicate bytes; the same network keeps its identity.
10. Hotspot: switch Wi-Fi to hotspot and back; per-network totals and per-app split follow the primary network.
11. VPN on: totals count VPN traffic once (on the physical interface), and the per-app sum does not exceed the network total.
12. Optional: measure CPU with the popover open and with two uplinks active (Wi-Fi plus Ethernet).
